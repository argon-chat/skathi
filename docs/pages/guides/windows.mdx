Every Skathi app has one main window, and `appWindow` is how your code talks to it. This guide follows that window from launch to quit. It shows where each setting belongs, how to minimize, maximize, pin and fullscreen the window, how to keep the UI in step with its state, and how to bring it back at the same size next time. Under Wayland on Linux, the compositor keeps an app from placing, hiding or pinning its own window, and each section says what that changes.

## The main window

A Skathi app has one JavaScript realm, one Vue or Svelte app and one element tree. The main window paints that tree. Pop-out windows (`<SkWindow>`) paint parts of the same tree, so they share state with the main window without messaging.

[`appWindow`](/window-api/app-window/) always addresses the main window, even when the code runs from an event handler inside a pop-out. The same is true of the web globals: `innerWidth`, `screenX`, `devicePixelRatio`, `screen`, `matchMedia()` and `document.title` all describe the main window.

```ts
import { getCurrentWindow } from "@skathi-native/runtime";
import { appWindow } from "skathi:app";

appWindow.title = "Notes";
console.log(getCurrentWindow() === appWindow);
```

[`getCurrentWindow()`](/window-api/get-current-window/) returns `appWindow` so that code ported from Tauri runs unchanged. It never returns a pop-out; pop-outs have no handle object.

Every `appWindow` verb is synchronous and returns `undefined`. There are no promises to await: the call is applied in the current frame, or queued to the top of the next one.

## The lifecycle, from launch to quit

1. **Launch.** With [`"singleInstance": true`](/window-api/config-single-instance/), a second launch hands its arguments to the running copy and exits without opening a window.
2. **Create.** The host reads the `window` block of `sk.config.json` and creates the window at that size and in its place: centred on the primary display unless [`x`, `y` and `monitor`](#start-position-and-monitor) say otherwise. On Windows, macOS and X11, the host keeps the window hidden during setup. Wayland maps the window when the compositor receives its first buffer.
3. **Run your bundle.** `appWindow` already works at the top level of `main.ts`. Reads return the initial state; verbs are queued and applied at the top of the first frame. [`DOMContentLoaded` and `load`](/window-api/event-load/) fire once, after the bundle has run.
4. **First frame.** The queued verbs are applied and window `resize` fires once. On Windows the host paints the first styled frame and only then shows the window, so there is no blank flash.
5. **Running.** State changes arrive as events and as reactive reads, covered in [Reactive reads and events](#reactive-reads-and-events).
6. **Close.** The user's close runs `close-requested`, then `beforeunload`, then `pagehide`. If nothing cancels it, every window of the app hides at once and pop-outs close.
7. **Quit.** Closing the main window quits the app on every OS, macOS included. localStorage, cookies and IndexedDB are flushed, and a 4-second deadline ends the process.

Steps 6 and 7 have their own guide: [Closing, hiding and quitting](/guides/closing-and-background/).

> **Tip:** Because verbs called at the top level of `main.ts` run before the window is revealed on Windows, a call such as `appWindow.maximize()` there makes the window appear maximized, not jump to it.

## Configure the window

There are three places to shape the window. They are not interchangeable: some settings exist only at creation time.

### sk.config.json

The [`window` block](/window-api/config-window/) is read once, before the window exists. It sets the initial size and minimum, the title bar style and whether the window can be resized, minimized or maximized. Changing it takes a restart.

```json
{
  "name": "notes",
  "productName": "Notes",
  "window": {
    "title": "Notes",
    "width": 960,
    "height": 640,
    "minWidth": 480,
    "minHeight": 320,
    "titleBarStyle": "default",
    "backdrop": "mica",
    "resizable": true
  }
}
```

The default `titleBarStyle` is `"hidden"`: your app draws its own title bar. This example asks for the OS caption instead. The [custom title bar guide](/guides/custom-title-bar/) covers the hidden style.

[`minWidth`](/window-api/config-window-min-width/) and [`minHeight`](/window-api/config-window-min-height/) each work alone; the other side is then not limited.

### Start position and monitor

[`x` and `y`](/window-api/config-window-x/) place the window when it is created, so it never shows at a default spot first. They are CSS px from the top-left corner of the monitor's work area, the part of the screen the taskbar or Dock leaves free. [`monitor`](/window-api/config-window-monitor/) picks the monitor: `"primary"` (the default), `"cursor"` for the one under the mouse pointer, or an index from `0`.

```json
{
  "window": { "width": 420, "height": 640, "x": 24, "y": 24, "monitor": "cursor" }
}
```

- An axis without a value is centred, so `{ "y": 0 }` opens at the top, centred horizontally. With neither, the window opens centred, which is what [`center: true`](/window-api/config-window-center/) also says. `center: true` together with `x` or `y` centres the window and warns.
- The window is kept inside the work area: an `x` past the right edge puts it against that edge, and a window larger than the work area is shrunk to fit. With `titleBarStyle: "default"` the OS caption stays on screen too.
- On Windows each monitor's own scale is used, so `x: 24` is 24 CSS px on a 100 % monitor and on a 200 % one alike.
- An index past the last monitor opens on the primary one and prints an advisory. Monitor indices follow the OS's own order, the same order as `<SkWindow :monitor>`.
- `"cursor"` is read on Windows only. On macOS and Linux the window opens on the primary monitor and an advisory says so. Under Wayland the compositor places the window and ignores `x` and `y`.

### defineWindow

[`defineWindow()`](/window-api/define-window/) is a convenience for the settings that can change at runtime. It runs when your bundle runs, after the window exists, and applies each key through the same setter a runtime call would use.

```ts title="main.ts" focus=4
import { createApp, defineWindow } from "@skathi-native/runtime";
import App from "./App.vue";

defineWindow({ title: "Notes", backdrop: "acrylic", alwaysOnTop: false });

createApp(App).mount();
```

A Svelte app imports `defineWindow` and `mount` from `@skathi-native/runtime/svelte` and calls `mount(App)` instead of `createApp(App).mount()`.

`defineWindow` accepts `title`, `backdrop`, `theme`, `alwaysOnTop`, `visibleOnAllWorkspaces`, `opacity`, `titleBarHeight` and `titleBarOverlay`. Set creation-time options such as `width` and `resizable` in `sk.config.json`. Passing one to `defineWindow` prints an advisory. An unknown key prints the list of accepted keys.

### Runtime calls

Everything else is a property or method of `appWindow`, plus the web globals. Changes made inside an input handler apply at once; changes made elsewhere apply at the next frame.

### Which layer sets what

| Setting                             | `sk.config.json`                          | `defineWindow` | At runtime                                                   |
| ----------------------------------- | ----------------------------------------- | -------------- | ------------------------------------------------------------ |
| Title                               | `title`                                   | yes            | [`appWindow.title`](/window-api/title/), `document.title`    |
| Initial size                        | `width`, `height`                         | no             | [`setContentBounds()`](/window-api/set-content-bounds/)      |
| Minimum size                        | `minWidth`, `minHeight`                   | no             | [`setMinSize()`](/window-api/set-min-size/)                  |
| Resizable, minimizable, maximizable | `resizable`, `minimizable`, `maximizable` | no             | no                                                           |
| Title bar style and fallback strip  | `titleBarStyle`, `titleBarFallback`       | no             | no                                                           |
| Title bar height and host buttons   | `titleBarHeight`, `titleBarOverlay`       | yes            | [`setTitleBarOverlay()`](/window-api/set-title-bar-overlay/) |
| Backdrop                            | `backdrop`                                | yes            | [`appWindow.backdrop`](/window-api/backdrop/)                |
| Always on top                       | `alwaysOnTop`                             | yes            | [`appWindow.alwaysOnTop`](/window-api/always-on-top/)        |
| `window.focus()` raises             | `focus: "raise"`                          | no             | no                                                           |
| Theme                               | `theme`                                   | yes            | [`appWindow.theme`](/window-api/theme/)                      |
| Start position and monitor          | `x`, `y`, `center`, `monitor`             | no             | [`setBounds()`](/window-api/set-bounds/)                     |
| Maximized, fullscreen               | none                                      | no             | `maximize()`, `setFullscreen()` at startup                   |

For development, `SK_WINDOW=1280x800` overrides the configured size without editing the config.

## Size, position and state

### Minimize, maximize and restore

/>

<Sample src="windows/WindowState" focus="state" />

The `computed` re-runs on its own: `appWindow` reads such as `isMaximized()` are reactive in templates, `computed` and `watch`. In Svelte the same reads are reactive in markup, `$derived` and `$effect`, so the `$derived` re-runs the same way. You never poll them.

- [`minimize()`](/window-api/minimize/) and [`maximize()`](/window-api/maximize/) ask the OS to change the state. Calling `maximize()` twice is harmless: it never toggles.
- [`unmaximize()`](/window-api/unmaximize/) and its alias [`restore()`](/window-api/restore/) restore from maximized, and also from minimized.
- [`toggleMaximize()`](/window-api/toggle-maximize/) maximizes a normal window and restores a maximized one.

On macOS, maximized means zoomed: `maximize()` zooms the window and `isMaximized()` is `true` while it is zoomed.

> **Note:** Under Wayland on Linux, the compositor does not report a minimized window. There, `isMinimized()` stays `false`, the `minimize` and `restore` events do not fire, and `restore()` cannot bring a window back from minimized.

### Fullscreen

<Demo id="windows/fullscreen" caption="A button enters fullscreen, and both the button and the Escape key leave it." />

<Sample src="windows/Fullscreen" />

There are two ways into fullscreen, and they differ in how the user gets out:

| Route                                                            | Escape leaves it | `document.fullscreenElement` | Typical use                      |
| ---------------------------------------------------------------- | ---------------- | ---------------------------- | -------------------------------- |
| [`element.requestFullscreen()`](/window-api/request-fullscreen/) | yes              | the element                  | a video, a slide, the whole page |
| [`appWindow.setFullscreen(true)`](/window-api/set-fullscreen/)   | no               | `null`                       | a kiosk mode the app controls    |

- Escape and [`document.exitFullscreen()`](/window-api/exit-fullscreen/) only undo element fullscreen. Leave window fullscreen with `appWindow.setFullscreen(false)`.
- Unlike in a browser, `requestFullscreen()` needs no click first. It rejects with a `TypeError` instead of firing `fullscreenerror`.
- On Windows, leaving fullscreen restores the exact earlier rect, maximized or not, on any monitor. On macOS fullscreen is native: an animated, separate Space. On Linux the window manager decides.
- [`isFullscreen()`](/window-api/is-fullscreen/) covers both routes, and the main window's [`fullscreenchange`](/window-api/event-fullscreenchange/) event fires for both.

While fullscreen, `@media (display-mode: fullscreen)` matches and `env(titlebar-area-*)` is undefined, so a custom title bar can hide itself with CSS alone.

[`appWindow.alwaysOnTop`](/window-api/always-on-top/) keeps the window above other apps' windows without taking focus. Set `"alwaysOnTop": true` in the `window` block to start pinned.

> **Note:** Under Wayland on Linux, an app cannot keep its window on top. Setting `alwaysOnTop` there prints an advisory and the getter stays `false`, so the button above keeps reading "Pin".

### Move and resize

| Call                                                        | Rect                  | Windows, macOS, Linux | Linux under Wayland         |
| ----------------------------------------------------------- | --------------------- | --------------------- | --------------------------- |
| [`setBounds(rect)`](/window-api/set-bounds/)                | outer, frame included | moves and resizes     | resizes; cannot move        |
| [`setContentBounds(rect)`](/window-api/set-content-bounds/) | client area           | moves and resizes     | resizes; cannot move        |
| [`window.resizeTo(w, h)`](/window-api/resize-to/)           | outer                 | resizes               | resizes                     |
| [`window.moveTo(x, y)`](/window-api/move-to/)               | outer                 | moves                 | does nothing, with advisory |
| [`center()`](/window-api/center/)                           | outer                 | centres               | does nothing, with advisory |

Both `setBounds()` and `setContentBounds()` take a partial rect in CSS pixels: `setBounds({ x: 100 })` moves without resizing. The size is clamped to the work area. On Windows, the position is clamped into the work area of the monitor the new rect lands on, so the window can move to another monitor but not behind the taskbar. On macOS and Linux, the position is not clamped.

`window.resizeTo()` and `window.resizeBy()` set the outer size, as in a browser. To size the client area, call `setContentBounds({ width, height })`.

## Reactive reads and events

### Reads

Every `appWindow` getter and every `is*()` and `get*()` method is reactive: [`isMaximized()`](/window-api/is-maximized/), [`isFocused()`](/window-api/is-focused/), [`getBounds()`](/window-api/get-bounds/), [`scaleFactor`](/window-api/scale-factor/), `title`, `theme`, `backdrop`, `chrome` and the rest. Read them in a template or a `computed` and Vue updates the UI when the window changes. In Svelte they are reactive in markup, `$derived` and `$effect`, once the app imports from `@skathi-native/runtime/svelte`.

The web globals are not reactive. `innerWidth`, `innerHeight`, `screenX` and `devicePixelRatio` are plain numbers; copy them into a `ref`, or a `$state` in Svelte, from a `resize` handler.

> **Note:** [`getBounds()`](/window-api/get-bounds/) and [`getContentBounds()`](/window-api/get-content-bounds/) return the last published state. Right after a `setBounds()` or `maximize()` outside an event handler, they can still return the old rect until the next frame. The `is*()` methods re-read the window and are exact.

### Events

The events are spread over four targets. `resize`, `focus` and `blur` fire on both the global `window` and `appWindow`.

| Event                                                                                    | Target                            | Fires when                                                                                | Windows | macOS   | Linux                     |
| ---------------------------------------------------------------------------------------- | --------------------------------- | ----------------------------------------------------------------------------------------- | ------- | ------- | ------------------------- |
| [`resize`](/window-api/event-resize/)                                                    | `window`, `appWindow`             | the viewport or the scale changes; once at start on `window`                              | yes     | yes     | yes                       |
| [`focus`](/window-api/event-focus/), [`blur`](/window-api/event-blur/)                   | `window`, `appWindow`             | the main window gains or loses activation                                                 | yes     | yes     | yes                       |
| [`maximize`](/window-api/event-maximize/), [`unmaximize`](/window-api/event-unmaximize/) | `appWindow`                       | the maximized state flips                                                                 | yes     | yes     | yes                       |
| [`minimize`](/window-api/event-minimize/), [`restore`](/window-api/event-restore/)       | `appWindow`                       | the window enters or leaves minimized                                                     | yes     | yes     | yes, not on Wayland       |
| [`move`](/window-api/event-move/)                                                        | `appWindow`                       | the outer position changed, once per frame                                                | yes     | partial | partial                   |
| [`fullscreenchange`](/window-api/event-fullscreenchange/)                                | `appWindow`                       | fullscreen by any route                                                                   | yes     | yes     | yes                       |
| [`backdropchange`](/window-api/event-backdropchange/)                                    | `appWindow`                       | `backdrop` or `effectiveBackdrop` changed                                                 | yes     | yes     | yes                       |
| [`visibilitychange`](/window-api/event-visibilitychange/)                                | `document`                        | minimized or hidden; on Windows also covered, on another desktop or, with the display off | yes     | partial | partial, never on Wayland |
| [`geometrychange`](/window-api/event-geometrychange/)                                    | `navigator.windowControlsOverlay` | the title bar area moved or resized                                                       | yes     | yes     | yes                       |
| [`close-requested`](/window-api/event-close-requested/)                                  | `appWindow`                       | the user asks to close                                                                    | yes     | yes     | yes                       |

Every host event is a plain `Event` with no payload. Read the new state from `appWindow` inside the handler; it is already current there.

<Sample src="windows/EventLog" />

### Order within a frame

The host collects changes once per frame and dispatches them in a fixed order: `resize` on `window`, then `visibilitychange`, then `resize` on `appWindow`, `maximize` or `unmaximize`, `minimize` or `restore`, `fullscreenchange`, `backdropchange`, `focus` or `blur` (on `window`, then on `appWindow`), `move`, `geometrychange`, and finally media query `change` events. The CSS environment is updated before the first of them, so `matchMedia()` in a `resize` handler already answers for the new size.

A verb called inside one of these handlers is applied at the next frame, not inside the dispatch.

## Remember the window's bounds

Skathi does not save the window's size, position or maximized state between launches. Store them yourself and apply them at startup.

<Sample src="windows/rememberBounds.ts" />

Call it before mounting, before `mount(App)` in a Svelte app:

```ts title="main.ts" focus=5
import { createApp } from "@skathi-native/runtime";
import App from "./App.vue";
import { rememberBounds } from "./rememberBounds";

rememberBounds();
createApp(App).mount();
```

The parts that matter:

- **Normal bounds, not current bounds.** A maximized window's rect is the work area, so the code keeps the last normal rect and a separate `maximized` flag. Restoring it puts the window back at its normal size, then maximizes it, so un-maximizing later lands where the user expects.
- **Skip minimized and fullscreen.** On Windows a minimized window reports a position around -32000. Saving that would park the window off screen next time.
- **Write on change, not only at exit.** The writes are debounced, so the state survives a crash too, and `pagehide` saves the last state on every close or quit, a tray `role: "quit"` item included. `localStorage` is flushed to disk when the app quits.
- **Startup timing.** The verbs are queued and applied at the first frame. On Windows that is before the window appears, so it shows at the saved place without jumping.

| Behavior                      | Windows | macOS                   | Linux                         |
| ----------------------------- | ------- | ----------------------- | ----------------------------- |
| Restore the size and position | yes     | yes, on the same screen | yes; only the size on Wayland |
| Restore the maximized state   | yes     | yes                     | yes                           |

> **Warning:** The window opens on the primary display, so the saved position is applied at that display's scale. On Windows, a position saved on a monitor with another scale factor lands off by the ratio of the two scales, then is clamped into the work area of the monitor it falls on. On macOS, positions are relative to the screen the window is on, so a position saved on another screen is applied to the screen the window opened on.

## DPI, coordinates and multiple monitors

Every number in the window API is in CSS pixels: device pixels divided by the window's scale factor. [`appWindow.scaleFactor`](/window-api/scale-factor/) and [`devicePixelRatio`](/window-api/device-pixel-ratio/) are the same value. When the window moves to a monitor with another scale, window `resize` fires and media queries on `resolution` are evaluated again.

Several reads describe different rectangles:

| Read                                                                                                                              | What it measures                             | Windows     | macOS and Linux                                                      |
| --------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- | ----------- | -------------------------------------------------------------------- |
| [`innerWidth`, `innerHeight`](/window-api/inner-width/)                                                                           | the box your app paints, without host chrome | yes         | yes                                                                  |
| [`appWindow.chrome`](/window-api/chrome/)`.client`                                                                                | the client area                              | yes         | yes                                                                  |
| [`getContentBounds()`](/window-api/get-content-bounds/)                                                                           | the client rect with its screen position     | client rect | macOS: the frame, title bar included, relative to the current screen |
| [`getBounds()`](/window-api/get-bounds/), [`screenX`, `screenY`](/window-api/screen-x/), [`outerWidth`](/window-api/outer-width/) | the outer rect, frame included               | yes         | same as `getContentBounds()`                                         |
| [`screen`](/window-api/screen/)                                                                                                   | the display the main window is on            | yes         | yes                                                                  |

- `innerWidth` is smaller than the client area only while the host draws its fallback title bar strip. Once your app draws its own title bar, the two are equal.
- On Windows, `outerWidth` minus `innerWidth` is the invisible resize border, not a title bar. Read the title bar height from `navigator.windowControlsOverlay.getTitlebarAreaRect()`.
- `screen.availLeft`, `availTop`, `availWidth` and `availHeight` give the work area of the current display, without the taskbar or Dock.

Multi-monitor support is limited today:

- `screen` describes only the display the main window is on. [`screen.isExtended`](/window-api/screen/) tells you whether there are others, and `window.getScreenDetails` is not defined.
- On Windows, `setBounds()` can move the window to another monitor; the position is then clamped into that monitor's work area.
- On Windows with monitors at different scales, `getBounds()` divides every coordinate by the window's current scale, so a position on another monitor is not in that monitor's CSS pixels.
- A pop-out can cover a chosen monitor with `<SkWindow cover="monitor" :monitor="1">`, on Windows only. The [pop-out guide](/guides/pop-out-windows/) shows it.

### Theme

[`appWindow.theme`](/window-api/theme/) is `"system"`, `"light"` or `"dark"`, like Electron's `nativeTheme.themeSource`. It drives `@media (prefers-color-scheme)` for the whole app, so the stylesheet above follows it with no extra code.

- It starts at `"system"` on every launch, or at `window.theme` from `sk.config.json`, which is in place before the window is first shown. It is not saved, which is why the sample stores the choice itself.
- Names are case-sensitive: `"Dark"` prints an advisory and is ignored.
- There is no theme event. To react in script, listen for `change` on `matchMedia("(prefers-color-scheme: dark)")`.

| Effect of `appWindow.theme`                    | Windows                                  | macOS                                    | Linux                  |
| ---------------------------------------------- | ---------------------------------------- | ---------------------------------------- | ---------------------- |
| `prefers-color-scheme` in CSS and `matchMedia` | yes                                      | yes                                      | yes                    |
| Native caption colours and backdrop tint       | yes, for every window, pop-outs included | yes, for every window, pop-outs included | no: they follow the OS |

On macOS the theme also reaches what AppKit opens for the app: the file dialogs, alerts, menus and the color panel. The traffic lights follow it too, so over a dark title bar on a Mac in light mode, set `"dark"` and the lights of an inactive window stay readable.

### Backdrop

[`appWindow.backdrop`](/window-api/backdrop/) picks the material behind your app: `"mica"` (the default), `"mica-alt"`, `"acrylic"`, `"transparent"` or `"none"`. The setter also accepts `"tabbed"`, `"blur"` and `"opaque"` as aliases. The material shows only where your app does not paint an opaque background, so keep the root and large panels translucent.

The getter returns the material actually applied. Set `"blur"` and it reads `"acrylic"`; on Windows builds before 22621, `"mica"` and `"mica-alt"` read back `"acrylic"`. [`effectiveBackdrop`](/window-api/effective-backdrop/) tells you what is drawn right now, and [`backdropchange`](/window-api/event-backdropchange/) fires when either value changes.

| Material                      | Windows 11 | macOS                                       | Linux                                         |
| ----------------------------- | ---------- | ------------------------------------------- | --------------------------------------------- |
| `mica`, `mica-alt`, `acrylic` | as named   | one behind-window blur for all three        | drawn opaque; `effectiveBackdrop` is `"none"` |
| `transparent`                 | yes        | yes                                         | depends on the compositor                     |
| `none`                        | yes        | yes                                         | yes                                           |
| In fullscreen                 | kept       | drawn flat; `effectiveBackdrop` is `"none"` | as above                                      |

> **Note:** Pop-out windows do not follow `appWindow.backdrop`. Each one takes the backdrop from its own `backdrop` prop, or else from the `backdrop` in `sk.config.json`.

## Taskbar and dock

| Feature                         | API                                                                                                              | Windows                    | macOS                 | Linux                                                               |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------- | -------------------------- | --------------------- | ------------------------------------------------------------------- |
| Name in the taskbar and Alt-Tab | [`appWindow.title`](/window-api/title/)                                                                          | yes                        | yes                   | yes                                                                 |
| Icon                            | [`windows.icon`](/window-api/config-windows-icon/), [`macos.icon`](/window-api/config-macos-icon/) at build time | yes                        | yes                   | from the `.desktop` entry matched by [`id`](/window-api/config-id/) |
| Badge                           | [`navigator.setAppBadge()`](/window-api/set-app-badge/)                                                          | a red overlay icon         | the Dock badge        | not available                                                       |
| Ask for attention               | [`window.focus()`](/window-api/window-focus/)                                                                    | flashes the taskbar button | bounces the Dock icon | X11 urgency hint; nothing on Wayland                                |
| Tray icon                       | [`appTray`](/window-api/app-tray/)                                                                               | yes                        | menu bar              | not available                                                       |
| Remove the taskbar button       | [`hide()`](/window-api/hide/)                                                                                    | yes                        | hides the window      | yes; minimizes instead on Wayland                                   |

`navigator.setAppBadge(n)` shows a number, `99+` above 99, or a dot with no argument; `0` or [`navigator.clearAppBadge()`](/window-api/clear-app-badge/) clears it. The runtime's typings declare both. They do not exist on Linux, so check before calling:

```ts
export async function showUnread(count: number): Promise<void> {
  if ("setAppBadge" in navigator) await navigator.setAppBadge(count);
}
```

By default `window.focus()` does not steal focus: it asks for attention instead. Set `"focus": "raise"` in the `window` block to make it bring the window to the front. `appWindow.show()` always raises.

> **Note:** There is no way to show taskbar progress or change the icon at runtime yet. Use `navigator.setAppBadge()` for badges.

## Pitfalls

- **Listening on the wrong target.** `maximize`, `minimize`, `move` and the other state events go to `appWindow` only, and `visibilitychange` to `document`. `resize`, `focus` and `blur` go to both `window` and `appWindow`.
- **Trusting a getter under Wayland.** There, `isMinimized()` is always `false` and `isVisible()` always `true`, because the compositor reports neither state.
- **Reading geometry right after a verb.** `getBounds()` can lag one frame behind `setBounds()`. Read the new rect in the `move` or `resize` handler instead.
- **Expecting a fixed window size from `innerWidth`.** It changes with host chrome and DPI; react to `resize` or use CSS media queries.
- **Unit tests.** Outside the host, `appWindow` is an inert stand-in: `is*()` methods return `false`, every other member is a no-op, and each access warns once.

## A mini player

Set the minimum and aspect ratio on the native content area, in CSS pixels. Passing `null` to either setter clears the constraint. A new minimum that exceeds the current size grows the window. `setMaxSize()` applies the upper bound.

```ts
appWindow.setMinSize({ width: 240, height: 135 });
appWindow.setAspectRatio(16 / 9);
appWindow.alwaysOnTop = true;
appWindow.visibleOnAllWorkspaces = true;
appWindow.setBounds({ width: 420 }, { animate: { duration: 180, easing: "ease-out" } });
```

On macOS both pinning properties together move the existing content into a nonactivating panel above other apps’ fullscreen Spaces. Clicking a field can give it keyboard focus while the other app keeps its menu bar. Clearing either property returns the content to its original window. Windows keeps the player above ordinary borderless fullscreen windows on its current desktop. Exclusive display modes, secure desktops and other topmost windows have their own ordering. X11 delegates both requests to the window manager. Wayland assigns stacking and workspace membership itself.

For a player that hides its controls when idle, use the caption-button rectangle before hiding the cursor. This example assumes a custom title bar extending across the viewport.

```ts
function hideControlsAt(x: number, y: number) {
  const r = appWindow.getWindowButtonsRect();
  if (r && x >= r.x && x < r.x + r.width && y >= r.y && y < r.y + r.height) return;
  appWindow.setWindowButtonsVisible(false, { fade: 150 });
}
```

Pass `PointerEvent.clientX` and `clientY` to this function. Call `setWindowButtonsVisible(true)` when the controls return. On Windows and Linux these methods address the Skathi caption overlay. On macOS they address the traffic lights and their current AppKit layout. [Caption button geometry](/window-api/get-window-buttons-rect/)

Use `appWindow.setFullscreen(true, { transition: "fade" })` to cover the content in black before macOS takes its fullscreen snapshot. Skathi reveals the content after AppKit completes or cancels the transition. The same option applies on exit. The existing `fullscreenwillchange`, `fullscreenchange` and `fullscreencancel` events report progress. Windows, Linux and reduced motion use the system transition. [Fullscreen options](/window-api/set-fullscreen/)

Use `hide({ fade: 150 })` and `show({ fade: 150 })` to fade to or from the window’s configured opacity. An animated bounds change lays out the content on each frame. Observe `move` and `resize` for intermediate and final bounds.
