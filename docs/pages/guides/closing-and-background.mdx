When the user clicks the close button, your app can let the window go, ask about unsaved work first, or hide and keep running in the background. This guide walks through the close flow event by event, then builds two complete scenarios: a "Save, Discard, Cancel" prompt and an app that hides on close and comes back on a second launch or a tray click. It ends with what happens at quit, how to make sure data reaches disk, and where macOS and Linux behave differently.

## The close flow

A close the user starts is any request that reaches the window through the OS or your title bar: the title bar's close button, a `--window-control: close` element or the host's caption close button, Alt+F4, Close in the taskbar menu, the red button on macOS, or a `WM_CLOSE` message from another program. Skathi runs it through three events, in order:

1. **`close-requested` on `appWindow`.** It is cancelable. If a listener calls `preventDefault()`, the window stays open and nothing else happens.
2. **`beforeunload` on `window`.** It runs only if `close-requested` was not cancelled. It can veto the close, but no dialog is ever shown.
3. **`pagehide` on `window`.** It runs once, if nothing vetoed. It is the last place to save state.

After `pagehide`, every window of the app hides at once, pop-outs close, and the app quits.

### close-requested

[`close-requested`](/window-api/event-close-requested/) is the event to build on. It fires before anything is torn down, and its `preventDefault()` works without the sticky-activation rule browsers apply to `beforeunload`, so an app the user has not touched yet can still hide instead of closing.

```ts
import { appWindow } from "skathi:app";

appWindow.addEventListener("close-requested", (e) => {
  if (hasUnsavedWork()) e.preventDefault();
});
```

The decision is synchronous. You cannot `await` a dialog inside the listener: call `preventDefault()` first, ask the user, and then close from code.

### beforeunload

[`beforeunload`](/window-api/event-beforeunload/) is there for code written for browsers. Its `preventDefault()` vetoes the close only after the user has pressed a key or a mouse button in the app, and even then Skathi shows no confirmation dialog: the close button simply does nothing. Use `close-requested` and your own UI instead. If a `beforeunload` listener vetoes a close and the app has no `close-requested` listener, Skathi prints a `beforeunload-trap` advisory.

### pagehide

[`pagehide`](/window-api/event-pagehide/) fires once per session, before the windows hide, on every way the app closes or quits. Synchronous `localStorage` writes made in it reach disk. [`unload`](/window-api/event-unload/) never fires; Skathi accepts the listener and prints an advisory, as the web is removing that event.

### Which routes run which events

| How the close starts                                                                     | `close-requested` | `beforeunload`   | `pagehide`    |
| ---------------------------------------------------------------------------------------- | ----------------- | ---------------- | ------------- |
| Title bar close, Alt+F4, taskbar Close, macOS red button, `WM_CLOSE`                     | yes               | if not cancelled | if not vetoed |
| `--window-control: close` or the host caption close button                               | yes               | if not cancelled | if not vetoed |
| [`appWindow.close()`](/window-api/close/), [`window.close()`](/window-api/window-close/) | no                | no               | yes           |
| A tray menu item with `role: "quit"`                                                     | no                | no               | yes           |
| A close from an embedding application                                                    | no                | no               | yes           |
| The session ending, or any other quit of the app                                         | no                | no               | yes           |
| Closing a pop-out window                                                                 | no                | no               | no            |

A pop-out cannot veto its own close; there is no `close-requested` for it. The [pop-out guide](/guides/pop-out-windows/) covers what happens to its content.

How it works:

- **Only dirty state cancels.** With nothing to save, the listener returns without calling `preventDefault()` and the window closes normally.
- **The sheet is your UI.** Skathi has no built-in confirmation dialog, so the prompt is an ordinary component. It can match your app and offer three choices instead of two.
- **`appWindow.close()` finishes the job.** It skips `close-requested` and `beforeunload`, so it does not loop back into the prompt, and it still fires `pagehide`.
- **Bring the window up first.** The taskbar's Close works on a minimized window. `restore()` brings it back so the user sees the question. Under Wayland on Linux, `isMinimized()` is always `false` and the line does nothing.

If the user clicks the close button again while the sheet is open, the listener cancels again and the sheet stays.

> **Warning:** An exception thrown in a `close-requested` listener counts as permission to close. Keep the listener small and make sure it cannot throw before `preventDefault()`.

## Hide instead of quitting

A timer, a chat client or a sync tool usually keeps running when its window closes. Cancel `close-requested`, hide the window, and give the user ways back: a second launch of the app, and a tray icon where there is one.

Turn on the single instance in `sk.config.json`, so a second launch reaches the running copy instead of starting another one:

```json title="sk.config.json" focus=3
{
  "name": "focus-timer",
  "singleInstance": true,
  "window": {
    "title": "Focus timer",
    "width": 420,
    "height": 300
  }
}
```

Then handle the close, the second launch and the tray in the root component:

### Hiding

[`appWindow.hide()`](/window-api/hide/) removes the window, and on Windows and Linux its taskbar button. The app keeps running: timers fire, network connections stay open and the UI keeps updating. While hidden, `document.hidden` is `true`, so the app gets no `requestAnimationFrame` callbacks and CSS animations pause.

### Coming back

- **A second launch.** With `"singleInstance": true`, starting the app again forwards its arguments to the running copy and exits without opening a window. The running copy receives a `launch` event on `appLaunch`, and the sample calls [`appWindow.show()`](/window-api/show/) from it.
- **The tray.** [`appTray`](/window-api/app-tray/) puts an icon in the Windows notification area or the macOS menu bar. Its `onClick` and a menu item call `show()`.
- **Under Wayland on Linux**, `hide()` minimizes the window instead, so it waits in the taskbar and the user restores it there like any minimized window.

`show()` shows a hidden window and brings it to the front. [`raiseOnSecondInstance`](/window-api/config-raise-on-second-instance/) (on by default) also raises the main window on a second launch, but call `show()` anyway: it is what makes a hidden window visible.

> **Warning:** On Windows and Linux a hidden window has no taskbar button. Without a tray icon and without `singleInstance`, a user who closes the window has no way to bring it back or quit, short of killing the process. Always offer at least one way back.

### The Quit item

The sample's tray menu uses its own item that calls `appWindow.close()`. The built-in `{ role: "quit" }` item does the same: it quits without `close-requested`, and `pagehide` fires first.

### Platform behavior

| Step                                       | Windows                    | macOS     | Linux                                       |
| ------------------------------------------ | -------------------------- | --------- | ------------------------------------------- |
| `hide()`                                   | hides; taskbar button goes | hides     | hides; minimizes instead under Wayland      |
| `singleInstance` and `launch`              | supported                  | supported | supported                                   |
| Raise on a second launch                   | supported                  | supported | supported; Wayland may only flag the window |
| `appTray`                                  | notification area          | menu bar  | not available: `available` is `false`       |
| Custom close button runs `close-requested` | yes                        | yes       | yes                                         |

## Close from code

[`appWindow.close()`](/window-api/close/) and [`window.close()`](/window-api/window-close/) are the same function. They fire `pagehide` synchronously and then close the main window, which ends the app.

- They do not fire `close-requested` or `beforeunload`. That is what lets an app that cancelled a close finish it after asking.
- They close the whole app. There is no way to close only the main window and keep pop-outs open; to close a pop-out, unmount its `<SkWindow>`.
- Calling them twice is harmless.
- Unlike in a browser, `window.close()` is not limited to windows a script opened.

## Quit and the data flush

Closing the main window quits the app on every OS. On macOS this differs from the platform convention: the app does not stay in the Dock without a window. Keep it running with `close-requested` and `hide()` instead.

When the app quits:

1. Every window of the app hides at once, so the user sees the close happen immediately.
2. Pop-outs close.
3. Skathi flushes `localStorage`, cookies and IndexedDB to disk.
4. A 4-second deadline ends the process, even if teardown is still running.

A second launch while the app is still closing waits for the old process to exit and then starts a fresh one.

To make data survive every way the app can end:

- **Write as you go.** `pagehide` runs on every close and quit, but not when the process crashes or is killed. Debounced `localStorage` writes during normal use cover those.
- **Keep `pagehide` synchronous.** Write to `localStorage` there. A `fetch()` or other asynchronous work started in `pagehide` is not guaranteed to finish before the process ends.
- **Do not rely on `unload`.** It never fires.

## Platform gaps

### Linux under Wayland: hide() minimizes

Under Wayland the compositor does not let an app hide its window, so `hide()` minimizes it. It stays in the taskbar, `isVisible()` stays `true` and no event fires.

## Pitfalls

- **Awaiting inside `close-requested`.** The veto is read when the listener returns. Call `preventDefault()` synchronously and ask afterwards.
- **Prompting from `beforeunload`.** It shows nothing, and without prior input it cannot veto. Use `close-requested`.
- **Saving only in `pagehide`.** It does not run when the process crashes or is killed.
- **Hiding with no way back.** Pair `hide()` with a tray icon or `singleInstance`.
- **Expecting the main window to close alone.** `appWindow.close()` ends the app, pop-outs included.
