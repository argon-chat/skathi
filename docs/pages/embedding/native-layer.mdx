[`<sk-surface>`](/embedding/native-frames/) takes frames and draws them as part of the page. A program that must present by itself, such as a player with its own swap chain and HDR output, wants the opposite: its own layer on screen, with the page over it. `<sk-layer>` is the element for that. It paints nothing; your layer is shown under the page where the element is.

```vue
<template>
  <sk-layer name="player" class="video" />
</template>
```

[The element's own page](/elements/sk-layer/) covers the app author's side. The page has to be transparent there to let the layer show. Nothing the page paints may cover the element: no background on it or on any of its ancestors. And the window's backdrop must be one that is not opaque, any [`backdrop`](/window-api/config-window-backdrop/) but `"none"`: `"transparent"`, or a material such as `"acrylic"` or `"mica"` where the platform has it. A window with `"none"` is drawn opaque and hides the layer. To keep the page from changing the backdrop, fix it with [`Builder::backdrop`](/embedding/desktop/#a-backdrop-the-page-cannot-change).

## The layer

Register a layer by name in `setup`. Each element of that name gets one of its own, made when the element is first painted and dropped when the element or its window goes.

```rust
use skathi::{Layer, LayerHost, LayerPlacement};

struct Player { /* your visual, swap chain, view */ }

impl Layer for Player {
    fn attach(&mut self, host: &LayerHost) {
        // Move the layer into this window; see below.
    }

    fn place(&mut self, placement: Option<LayerPlacement>) {
        match placement {
            Some(at) => { /* show at at.bounds, clipped to at.clip */ }
            None => { /* hide */ }
        }
    }
}

let builder = skathi::Builder::new().setup(|host| {
    host.layer("player", || Box::new(Player::new()));
    Ok(())
});
```

- **`attach`** is called when the element is painted in a window for the first time, when it moves to another window, when the window's view is moved into another native window or under another superview (macOS), and when the window rebuilt what it composes with (a lost device on Windows). A placement always follows it.
- **`place`** is called from the paint that draws the element, before that frame is presented, and only when the placement changed. `None` means the element was not painted in the last frame: `display: none`, scrolled out, or culled.
- **`presented`** (optional, Windows) is called once Skathi has committed your changes with the frame that carried them; see below.
- **`stack`** (optional) gives the layer its place among the `<sk-layer>` elements of its window in paint order, `0` at the bottom. It is called before `place` when that place changes. A layer painted later lies over an earlier one: put your visuals in that order.
- **`frame_submitted`** (optional) is called for every page frame of the layer's window while the layer is placed, on Windows, macOS and Linux; see [Frames of the page](#frames-of-the-page).
- **`picture`** (optional) names a surface whose frames stand in for the layer in backdrop effects; see [What backdrops see](#what-backdrops-see).
- All run on Skathi's UI thread inside the page's paint or present. Return quickly and do not call into Skathi from them.

`LayerPlacement` is in device pixels of the window:

| Field     | Means                                                           |
| --------- | --------------------------------------------------------------- |
| `bounds`  | the element's box: `[x, y, width, height]`                      |
| `clip`    | the part of it inside the clips of its ancestors                |
| `radii`   | its corner radii, top-left clockwise                            |
| `scale`   | the window's scale factor                                       |
| `opacity` | the opacity the element is shown at: its own and its ancestors' |

A CSS transform on the element or an ancestor is not applied to the placement.

`radii` are the element's own corners. An ancestor with `border-radius` and `overflow: hidden` clips the page's content but not your layer: `clip` is only the rectangle the ancestors leave. To round the layer, give `<sk-layer>` its own `border-radius`, the same as the ancestor's.

## Where the layer goes

`LayerHost` says where, per platform:

| Field           | Means                                                                                          |
| --------------- | ---------------------------------------------------------------------------------------------- |
| `window`        | the window's Skathi ID                                                                         |
| `handle`        | the raw window handle: the `HWND`, on macOS the `NSView` the page is drawn in                  |
| `composition`   | Windows: the window's `IDCompositionDevice` and the `IDCompositionVisual` drawn under the page |
| `native_window` | macOS: the `NSWindow` the page's view is in now                                                |

**Windows.** Skathi's window owns the DirectComposition target, so a target of your own is refused and a child window lands over the page. Create your visual on `composition.device` (a visual belongs to the device that made it) and add it to `composition.underlay`. Both pointers are borrowed for the call: clone the interfaces to keep them, and drop the old ones on the next `attach`.

```rust
fn attach(&mut self, host: &LayerHost) {
    let Some(composition) = host.composition else {
        return; // no DirectComposition in this window: nothing can be shown under it
    };
    let (device, underlay) = unsafe {
        (
            IDCompositionDevice::from_raw_borrowed(&composition.device.as_ptr()).unwrap().clone(),
            IDCompositionVisual::from_raw_borrowed(&composition.underlay.as_ptr()).unwrap().clone(),
        )
    };
    // create the visual on `device`, set its content, underlay.AddVisual(&visual, true, None)
}
```

`composition` is `None` when the window does not present through DirectComposition; that is the answer to whether a layer can be shown under this window at all.

**Do not call `Commit` from `attach` or `place`.** The device is shared, and Skathi commits it right after it presents the frame those calls came from, so your visual's changes and the page's frame go out together, and a frame that is dropped (during a live resize) does not leave the layer ahead of the page. A hide is committed at once, since the frame without the element is already on screen. `presented` tells you when that commit was made. A `Commit` of your own still works, but it reaches the compositor before the page's frame does.

What Skathi commits is the visual: its offset, clip and transform. If the layer's content must be redrawn at a new size, as a player's swap chain is after a resize, that picture reaches the screen when your renderer presents it. To keep it in the page's frame, present it before `place` returns, or scale the last picture with the visual's transform until your renderer catches up.

**macOS.** `handle` is `RawWindowHandle::AppKit`, whose `ns_view` is the view the page is drawn in. Add your view to its superview, below it (`addSubview:positioned:relativeTo:` with `NSWindowBelow`), so it stays inside the window's content view and moves with it.

When your program moves that view, or the content view holding it, into a window of its own, the page is redrawn there and `attach` is called again with the same `window` and `handle` and the new `native_window`, then `place`. Read the view's `superview` again then: a view of yours that moved with the content view needs nothing more; one left behind belongs under the view's new superview.

### A window Skathi did not create

While the page's view is in a window of yours, Skathi's window follows the view there:

- **Goes to your window:** what the page asks of its window (title, size and position, minimize, zoom, fullscreen, always on top, opacity, size limits), and what Skathi reads from it (bounds, screen and scale, appearance, key status, occlusion, the mouse position).
- **Heard from your window by notification:** moves, screen changes, occlusion, becoming and resigning key, and entering and leaving fullscreen. Skathi does not replace your window's delegate.
- **Stays with Skathi's own window:** its delegate, window tabs, restorable state, the backdrop (the window's background colour, whether it is opaque, and the blur behind it), and Skathi's titlebar chrome (button positions, titlebar transparency, the fullscreen desktop picture). Your window keeps all of these as you set them. A see-through backdrop still makes the page's own layer see-through, so your window shows under the page.
- **Not handled:** files dragged onto your window, which reach the page only in Skathi's own window.

Skathi's own window keeps no part in the page meanwhile: its delegate is ignored, and closing it by hand closes only that empty window. Skathi retains your window while the view is in it.

When the page closes, by `appWindow.close()`, by `Handle::close` or by a close request from its own window controls, it ends as it does in its own window: a close that asks first (`close-requested`, `beforeunload`) asks here too and can be refused, the [close events](/guides/closing-and-background/) fire, and your close hooks run. Skathi then takes its view out of your window, stops listening to it and releases it, and its own empty window goes with the page. Your window is not closed, hidden or changed otherwise. The view goes back into Skathi's window; if you moved Skathi's content view into your window too, only the page's view is taken out of it, and the content view stays where you put it. Do not keep using the view after the page has closed.

**Linux.** `attach` and `place` are called, but there is no place under the page yet.

## What backdrops see

The layer is composed under the page by the platform, after Skathi has drawn its frame, so `backdrop-filter` and [backdrop effects](/guides/shader-library/) over the element see only the page: a frosted panel over your video blurs a transparent hole. To fix that, give Skathi a picture of the layer. `picture` returns a [`SurfaceHandle`](/embedding/native-frames/), asked once when the layer is made, and you present your frames to it as to any `<sk-surface>`:

```rust
impl Layer for Player {
    fn picture(&mut self) -> Option<SurfaceHandle> {
        Some(self.picture.clone()) // skathi::surface("player-picture"), made once
    }
    // attach, place, ...
}

// On the player's thread, after each frame it presents itself, the same picture
// through any of the surface's present calls:
if picture.info().visible {
    picture.present_bgra(&pixels, width, height, width as usize * 4)?;
}
```

- **Only backdrops see it.** The picture is never drawn into the page. Backdrop readers whose region meets the layer see the page over the picture, cut to the layer's box, `clip` and rounded corners, faded by its opacity, and fitted into the box by the element's `object-fit` and `object-position` (`fill` by default). Outside their shapes the page stays as it is, with its own alpha, so the live layer keeps showing through.
- **Present while it is visible.** `info().visible` is true while a backdrop of the layer's window sampled the picture in the frame last drawn there, or while an `<sk-surface>` showing the same surface can be on screen; a `SurfaceEvent::Changed` tells you when that flips. While neither holds, presents are accepted but redraw nothing, and Skathi does not wake for them. A new frame redraws only the windows that read or show it, and only when it is newer than the one shown.
- **A reader that appears.** Reads are known once a frame is drawn, so the first frame drawn with a new reader shows the picture the layer held before: nothing the very first time, the last frame written otherwise. If a frame is already presented, the next frame shows it. If you only start presenting when `visible` turns true, add your own latency to that. To keep the gap to one frame, present your newest frame even while `visible` is false, or at least the last one before you stop: such a present only stores the frame.
- **Frame events mean the page.** `FrameEvent::Presented` for the picture's frame M means the page frame that composited M was presented, timed like `<sk-surface>` frames. A frame no page frame composited before a newer one arrived is `Dropped` as `Superseded`, and one presented while nothing reads or shows it is `Dropped` as `Hidden`.
- **The same surface in the page.** A surface can be a layer's picture and be shown by `<sk-surface>` elements at the same time. Each use works as it would alone: the elements update as any `<sk-surface>` does, readers see the picture, and a frame is `Presented` when either use put it on screen.
- **Colour** is handled as on `<sk-surface>`: 8-bit frames are sRGB, half-float frames are mapped to the window's headroom. A proxy does not switch its window to HDR output; it keeps extended range when the window is already HDR. The picture keeps its alpha.
- **Several layers.** Pictures stack in the elements' paint order, the one painted last on top, the same order `stack` tells you. Every reader on the page sees every picture under it, including one whose element is painted after the reader.
- **Where it applies.** Readers drawn straight into the window see pictures: `backdrop-filter` and backdrop effects on ordinary elements. Readers inside an isolated group (an element with a filter, a mask, `mix-blend-mode`, or a content effect) see only what the group drew, as before. The D3D12, Metal and wgpu renderers composite pictures; the Direct3D 11 fallback does not, and its readers see the page alone. A window with no picture costs nothing: no extra pass and no extra texture.

## Frames of the page

`frame_submitted` hears each page frame of the layer's window while the layer is placed, with a `LayerFrame`:

| Field               | Means                                                                                                                                                                                                                                                                          |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `sequence`          | The page frame's number in its window, starting at 1.                                                                                                                                                                                                                          |
| `submitted_at`      | When the page frame was handed to the platform, on the `monotonic_ns` clock.                                                                                                                                                                                                   |
| `picture`           | The ID returned by the surface present for the picture a backdrop composited from this layer. It repeats when another page frame uses the same picture. `None` when this page frame used no picture from this layer, even if an inline `<sk-surface>` showed the same surface. |
| `target_present_at` | The target time for showing this page frame, on the same clock. The macOS `CAMetalDisplayLink` supplies it for its drawable. `None` on other paths, including `nextDrawable`.                                                                                                  |

It runs on the UI thread, right after the window's present call returns: after `Present` on the swap chain (Windows), after the frame is committed to the layer tree (macOS), after the frame is submitted (Linux). `presented` is unchanged: on Windows it still comes only after a frame that carried `attach` or `place` changes, once Skathi has committed them. For when a frame reached the screen, use the picture's `FrameEvent::Presented`.

A player can match `picture` against its outstanding frame IDs and schedule its own drawable for `target_present_at` when available. The target is a scheduling hint.
