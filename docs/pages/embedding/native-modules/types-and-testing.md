Your exe knows its [native modules](/embedding/native-modules/): their functions, their parameters and every type they reach. It writes that down as TypeScript for the app, so the app's type check catches a renamed field before a user does. This page covers that file, how to test a module on both sides, and the checks that keep them honest in CI.

## The generated declarations

From the module signatures and their `#[skathi::data]` types, your executable describes its modules in TypeScript, and the CLI writes them into the app:

```sh
cargo build
cd app && bunx sk types --exe ../target/debug/notes.exe
```

That writes `app/src/native-modules.d.ts`, beside the app's entry:

```ts title="app/src/native-modules.d.ts"
// The native modules of the program that embeds this app. Generated by `sk types`; do not edit.

declare module "native:notes" {
  export type Note = {
    id: number;
    title: string;
    body: string;
  };
  export type SearchOptions = {
    limit: number | null;
  };
  export type SyncProgress = {
    done: number;
    total: number;
  };
  export const available: boolean;
  export function get(id: number): Note;
  export function search(text: string, options: SearchOptions): Promise<Note[]>;
  export function on(event: "progress", handler: (data: SyncProgress) => void): () => void;
  export function off(event: "progress", handler: (data: SyncProgress) => void): void;
}
```

- **Every type a module reaches is declared inside it**, exported, so the app imports types and functions from the same place: `import { get, type Note } from "native:notes"`. A type two modules use is declared in each.
- **A function returns its `Ok` type**; a task returns a `Promise` of it.
- **Trailing `Option` parameters are optional** (`max?: number | null`).
- **Bytes** are a `Uint8Array` in results and fields; a `&[u8]` or `Vec<u8>` parameter takes `ArrayBufferView | ArrayBuffer`, and `&[f32]` a `Float32Array`. The [type table](/embedding/native-modules/values/#the-type-table) has the rest.
- **Each module has `available`**, and `on`/`off` overloads for exactly the events it declares, with each handler's data typed.
- **Two different types with the same name in one module** fail the generation with a message that says to rename one: `#[serde(rename = "…")]` changes the name the app sees.

[`sk dev --exe`](/embedding/dev-loop/) does the same every time it starts, and writes the file only when it changed. Commit it: the app then type-checks and builds without your Rust toolchain. Without it, TypeScript stops at the import with `Cannot find module 'native:notes'`, the reminder to run `sk types`.

The `types` feature (on by default) is what pulls in [specta](https://docs.rs/specta). Off, `#[skathi::data]` derives serde only, `sk types` says the exe was built without it, and the modules work the same.

## Answer sk types before anything else

`sk types` runs your exe with `--sk-host-types`. `Builder::spawn` (and `run_on_main_thread`) see the flag, print the declarations and end the process before a window, a payload or a data directory is touched. Everything your `main` does _before_ it reaches `spawn` still runs, though: opening a log file, starting crash reporting, taking a single-instance lock, registering with the OS. For `sk types` that is wasted work at best, and at worst a crash-reporting session or a log entry for a run that never was.

Check the flag first and build only the modules:

```rust
fn main() {
    if std::env::args().nth(1).as_deref() == Some("--sk-host-types") {
        let _ = register(skathi::Builder::new(), &Arc::new(Services::default())).spawn();
        return;
    }
    // Logging, crash reporting, the single-instance lock, …
    let services = Arc::new(Services::default());
    let ui = register(skathi::Builder::new(), &services)
        .payload_file("app/dist/release/.sk/app.skpk")
        .spawn();
    // …
}
```

`register` is the function that adds every module ([several modules, one state](/embedding/native-modules/#several-modules-one-state)), so the declarations always match what the real run registers. The module values only have to exist: nothing runs, so constructing their state should be cheap and free of side effects. Keep threads and connections for `setup`.

## Keep it current in CI

The declarations are generated from the exe, so they go stale the moment a Rust signature changes and nobody regenerates. Two checks catch it, after the exe is built:

```sh
cargo build --release
cd app
bunx sk types --exe ../target/release/notes.exe
git diff --exit-code src/native-modules.d.ts   # the committed file is what the exe says
bunx vue-tsc --noEmit                          # the app agrees with it
```

`sk types` exits non-zero when the exe cannot describe its modules (a module error, or an exe without the `types` feature), and prints `unchanged` when the file already matches. A failed `git diff` names the signature that moved; regenerate and commit it with the Rust change.

## Testing a module in Rust

A module is a plain Rust type, and its exported methods are plain methods. Test them as such, with no engine and no window:

```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn a_title_becomes_a_slug() {
        let tools = Tools;
        assert_eq!(tools.slug("Groceries for Sunday".into(), None).unwrap(), "groceries-for-sunday");
        assert!(tools.slug("   ".into(), None).is_err());
    }
}
```

That covers the logic, which is most of a module. What it does not cover is the crossing: field names after `rename_all`, a `skip` that should not have been, an enum's tag. Those show up in the generated declarations, which is why the CI check above diffs them: a renamed field changes the `.d.ts`, and a reviewer sees it.

## Testing the app's side

App code that imports `native:…` is tested where it runs.

**In the real host**, give the test run a module of its own that reports back, and a small payload that calls your modules and the probe in turn. The program starts hidden, the probe module hands the result to the test's thread, and the test closes the app:

```rust
let (report, results) = std::sync::mpsc::channel::<Result<String, String>>();
let ui = register(skathi::Builder::new(), &services)
    .module("probe", move |m: &mut skathi::Module| {
        m.function("done", move |passed: bool, detail: String| {
            let _ = report.send(if passed { Ok(detail) } else { Err(detail) });
        })
        .params(["passed", "detail"]);
    })
    .payload_file("tests/probe/dist/debug/.sk/app.skpk")
    .visible(false)
    .activate(false)
    .spawn()
    .expect("spawn");
let result = results.recv_timeout(std::time::Duration::from_secs(30));
ui.close();
assert!(matches!(result, Ok(Ok(_))), "{result:?}");
```

```ts title="tests/probe/src/main.ts"
import * as notes from "native:notes";
import { done } from "native:probe";

void (async () => {
  if (!notes.available) throw new Error("native:notes is not registered");
  const found = await notes.search("todo", { limit: 1 });
  done(true, `${found.length} note(s)`);
})().catch((e) => done(false, String(e)));
```

This is the test that catches the crossing for real: argument names, `Result` errors, tasks settling, events arriving. Set `SK_WINDOW_FOCUS=never` in its environment so the window never takes the foreground.

**With the devtools**, a running app is scriptable: [`eval`](/devtools/scripting/) runs code in the page, and `__sk_native_module("notes")` there returns the object that `import … from "native:notes"` reads, so a script can call a function or subscribe to an event of the live app:

```sh
ctl=node_modules/@skathi-native/cli/devtools/ctl.ts
bun $ctl --app notes eval '__sk_native_module("notes").get(1).title'
```

`--app` takes the `name` from the payload's `sk.config.json` and attaches to the newest running copy. When an installed copy of the same app runs too, pin yours with `--dist`: on Windows each copy's folder is `%TEMP%\skathi\apps\<name>\<pid>`.

## The same code in a web build

Skathi's builders (`sk dev`, `sk build`) resolve `native:*` themselves: to your program's module when it is embedded, to the [stand-in](/embedding/native-modules/#one-app-with-or-without-a-program) otherwise. Another tool building the same source, a Vite web build of the app or vitest, does not know the scheme and stops at the import. Give it the same stand-in, made from the declarations you already commit:

```ts title="native-modules.vite.ts"
import { readFileSync } from "node:fs";
import type { Plugin } from "vite";

/** `native:*` outside Skathi: `available` is false, functions throw, `on` never fires. */
export function nativeModules(declarations: string): Plugin {
  return {
    name: "native-modules",
    enforce: "pre",
    resolveId: (id) => (id.startsWith("native:") ? `\0${id}` : null),
    load(id) {
      if (!id.startsWith("\0native:")) return null;
      const name = id.slice("\0native:".length);
      const text = readFileSync(declarations, "utf8");
      const block = text.slice(text.indexOf(`declare module "native:${name}"`)).split("\n}")[0] ?? "";
      const names = new Set([...block.matchAll(/export function (\w+)\(/g)].map((m) => m[1]));
      const lines = [
        "export const available = false;",
        "export const on = () => () => {};",
        "export const off = () => {};",
      ];
      for (const fn of names) {
        if (fn !== "on" && fn !== "off")
          lines.push(`export function ${fn}() { throw new Error("native:${name} needs the desktop app"); }`);
      }
      return lines.join("\n");
    },
  };
}
```

Add `nativeModules("src/native-modules.d.ts")` to the `plugins` of `vite.config.ts` and of each vitest project. The browser build then runs the `available === false` branches, and a vitest test replaces a module like any other:

```ts
vi.mock("native:system", () => ({
  available: true,
  openUrl: vi.fn(async () => true),
}));
```
