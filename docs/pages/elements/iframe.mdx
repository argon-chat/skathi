Sometimes part of the app already exists as a web page: a help center, your service's account or billing page, a report a server renders as HTML, a third-party widget. `<iframe>` shows it inside the app, under your own UI, without rewriting it.

Skathi has no browser engine of its own, so the document runs in the system's webview, WebView2 on Windows and WebKit's WKWebView on macOS, in a separate browser process, and is composited into the element's box. It is the one place in a Skathi app where HTML and its JavaScript run in a real browser, with its own network stack, cookies and sandbox. The document is not a Skathi component: it cannot import your Vue or Svelte code or reach your state, and the two sides talk through `postMessage`.

Where the system has no webview Skathi can use, an `<iframe>` is an empty box that fires `error`, so check `skFeatures.iframe` and offer a fallback. [Platforms](#platforms) lists where it works and how the two webviews differ.

## Help pages from the app's files

HTML that ships with the app loads from a relative path, served by Skathi from the package. Messages go both ways: the app calls `postMessage` on the iframe's `contentWindow`, and the document answers with `window.parent.postMessage`, which arrives as a `message` event on `window`.

```vue title="Help.vue" framework="vue"
<script setup lang="ts">
import { onMounted, onUnmounted, ref } from "vue";

const frame = ref<HTMLIFrameElement | null>(null);
const reply = ref("");
const webView = skFeatures.iframe;

function onMessage(e: MessageEvent) {
  if (e.source === frame.value?.contentWindow) reply.value = String(e.data);
}
onMounted(() => window.addEventListener("message", onMessage));
onUnmounted(() => window.removeEventListener("message", onMessage));

function ping() {
  frame.value?.contentWindow?.postMessage({ type: "ping" });
}
</script>

<template>
  <iframe v-if="webView" ref="frame" class="doc" src="help/index.html" />
  <p v-else>Help is not available on this system.</p>
  <button @click="ping">Ping</button>
  <p>{{ reply }}</p>
</template>

<style scoped>
.doc {
  width: 100%;
  height: 480px;
  border: 0;
}
</style>
```

```svelte title="Help.svelte" framework="svelte"
<script lang="ts">
  let frame = $state<HTMLIFrameElement>();
  let reply = $state("");
  const webView = skFeatures.iframe;

  function onMessage(e: MessageEvent) {
    if (e.source === frame?.contentWindow) reply = String(e.data);
  }

  function ping() {
    frame?.contentWindow?.postMessage({ type: "ping" });
  }
</script>

<svelte:window onmessage={onMessage} />

{#if webView}
  <iframe bind:this={frame} class="doc" src="help/index.html" title="Help"></iframe>
{:else}
  <p>Help is not available on this system.</p>
{/if}
<button onclick={ping}>Ping</button>
<p>{reply}</p>

<style>
  .doc {
    width: 100%;
    height: 480px;
    border: 0;
  }
</style>
```

Inside `help/index.html`, the document answers with `window.parent.postMessage("pong", "*")`. Compare `e.source` with the iframe's `contentWindow`, as the sample does, so a message from somewhere else is not taken for the document's.

## A page from the web, with a fallback

A page from your web service loads from its `https:` URL. Show a loading state until `load`, and treat `error` as real: unlike a browser, Skathi fires it when the page fails to load, when there is no webview, or when too many documents are open. Where there is no webview at all, a plain link opens the page in the system browser instead.

```vue title="Account.vue" framework="vue"
<script setup lang="ts">
import { ref } from "vue";

const url = "https://example.com/account";
const webView = skFeatures.iframe;
const state = ref<"loading" | "ready" | "failed">("loading");
</script>

<template>
  <div v-if="webView && state !== 'failed'" class="frame">
    <p v-if="state === 'loading'">Loading…</p>
    <iframe
      class="page"
      :src="url"
      sandbox="allow-scripts allow-forms allow-same-origin"
      @load="state = 'ready'"
      @error="state = 'failed'"
    />
  </div>
  <a v-else :href="url">Open your account in the browser</a>
</template>

<style scoped>
.page {
  width: 100%;
  height: 600px;
  border: 0;
}
</style>
```

```svelte title="Account.svelte" framework="svelte"
<script lang="ts">
  const url = "https://example.com/account";
  const webView = skFeatures.iframe;
  let state = $state<"loading" | "ready" | "failed">("loading");
</script>

{#if webView && state !== "failed"}
  <div class="frame">
    {#if state === "loading"}
      <p>Loading…</p>
    {/if}
    <iframe
      class="page"
      src={url}
      title="Account"
      sandbox="allow-scripts allow-forms allow-same-origin"
      onload={() => (state = "ready")}
      onerror={() => (state = "failed")}
    ></iframe>
  </div>
{:else}
  <a href={url}>Open your account in the browser</a>
{/if}

<style>
  .page {
    width: 100%;
    height: 600px;
    border: 0;
  }
</style>
```

`sandbox` is the browser's real sandbox; without it the document is not sandboxed. `load` and `error` fire once per navigation of the element, not for links the user follows inside the page. A `postMessage` to a document from the web needs its origin, or `"*"`, as the target origin.

## Things to watch for

- **Not on every system.** Check `skFeatures.iframe`; it is `false` where the system has no webview Skathi can use, on Windows without the WebView2 runtime, and in a host built without the `webview` feature.
- **Two engines.** The document runs in Chromium on Windows and WebKit on macOS. A page from the web that signs in with cookies may not work on macOS, where WebKit blocks third-party cookies; see [Platforms](#platforms).
- **Your UI draws over it, its background does not show under it.** The document is drawn under the app through a hole cut in the app's drawing, so a menu over the iframe draws on top, but `opacity` on the iframe does not reach the document.
- **No permissions.** Skathi denies every permission request from the webview: no camera, microphone, location or notifications, whatever `allow` says.
- **Eight at most.** At most 8 documents are open at once across the app; the ninth `<iframe>` fires `error`.
- **Changing an attribute reloads.** A changed `src`, `sandbox` or other attribute rebuilds the document from scratch and drops messages queued for the old one.

## What it can load

| `src`                                             | Loads                                                                                                                    |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| A relative or root-relative path, `app://redjs/…` | The app's own file, served by Skathi from the package, or in development from the app's root or its `public/` directory. |
| `https:`, `data:`, `//host/…`                     | Loaded by the webview from the network, with its own network stack, cache and cookies.                                   |
| `srcdoc`                                          | That HTML. It wins over `src`.                                                                                           |

Inside the webview, the app's files are served from an origin of their own: `https://app.vn.invalid` on Windows, a name that never resolves, so a request Skathi does not answer fails instead of going to the network, and `sk-app://app` on macOS, a scheme only Skathi answers. Either is a secure context. A document from the app's files sees that origin as its `location.origin` and as the origin of messages from the app. The app sees its own origin in messages from such a document.

## Attributes

`src`, `srcdoc`, `sandbox`, `allow`, `referrerpolicy`, `name` and `allowfullscreen` are passed to the document as a browser would apply them. Changing any of them navigates again: the document is rebuilt from scratch, and messages queued for the old one are dropped. `width` and `height` are size hints in CSS pixels, unitless; CSS wins.

`loading` is reflected but ignored: the document is created as soon as the element is in the document, on screen or not. `allow` grants nothing in practice, because every permission request from the webview is denied.

## Messaging

**From the app.** `iframe.contentWindow` is an object with only `postMessage` (and `toString`), the same object each time, and `null` while the element is not in the document. `contentDocument` is always `null`: the document is cross-origin.

`postMessage(message, targetOrigin)` sends to the document. The target origin defaults to `"/"`, the app's own origin, which reaches a document from the app's files. Pass the document's origin, or `"*"`, for one from the web, and `"*"` for a document sandboxed without `allow-same-origin`, whose origin is opaque. A message is encoded in the sender, so a value that cannot cross throws there: JSON values, `undefined`, `NaN`, the infinities, `-0`, BigInt, `Date`, `ArrayBuffer`, typed arrays, `DataView`, `Map`, `Set` and plain objects can; functions, symbols, elements, cyclic objects and transfer lists cannot. A message sent before the document is ready waits for it; one sent to an element without a document is dropped.

**From the document.** The document calls `window.parent.postMessage(…)`. The app gets a `message` event on `window`, not on the element, with `source === iframe.contentWindow`, `origin` and `data`. `ports` is always empty. Only the iframe's own document reaches the app; frames nested in it and popups it opens do not.

## Events

`load` and `error` fire once per navigation of the element: when it is created, and after each change of `src` or the other attributes above. Links followed inside the document fire nothing. Unlike a browser, which never fires `error` on an iframe, Skathi fires `error` when the page fails to load or its server answers with an HTTP error, when there is no webview, when the browser process exits, or when too many documents are open. The reason goes to the console.

## Input and focus

An `<iframe>` is focusable by default. While it has focus, the keyboard goes to the document, input methods included, except F5, F11, F12 and Escape while the app is full screen, which stay with the app. On Windows, combinations with Alt stay with the app too; on macOS, a Command shortcut the document does not use goes on to the app and its menus. `Tab` past the document's last focusable element, or `Shift+Tab` past its first, moves the focus to the app's next or previous element; with nothing else to focus, the document keeps it.

Mouse buttons (left, middle, right) and the wheel go to the document where the app's hit test lands on the iframe's box, so an element positioned over the iframe gets the clicks there. On Windows, Shift and Ctrl are passed with them, Alt and the Windows key are not, and one wheel notch scrolls 100 pixels. On macOS the document gets the system's own events, with every modifier, and trackpad scrolling keeps its momentum and bounce. Touch and pen input is not forwarded, and neither are trackpad pinches. The cursor follows the document's.

## Size and CSS

The box is 300 × 150 unless CSS sizes it, as in browsers. The webview is placed at the box, clipped to it and to clipping ancestors, and scaled with the window. `border-radius` rounds the visible corners.

The document is drawn under the app: Skathi cuts the iframe's box out of its own drawing, so the document shows through. The element's own `background` therefore does not show under the document, and an element positioned over the iframe draws over the document. `opacity` on the iframe is not applied to the document, and the effect of `transform` on it is not defined.

When the iframe is not painted (`display: none`, scrolled out of view), its document is hidden but keeps running.

## Lifecycle and limits

- A document exists while the element is in the document and has a `src` or `srcdoc`. Moving the element keeps its document; removing it closes the document.
- At most 8 documents are open at once, across the app. The ninth `<iframe>` fires `error`.
- The webview's own top-level navigation, new windows and popups are blocked. `alert()`, `confirm()` and `prompt()` show no dialog. A file input opens the system's file picker.
- Zooming, swipe navigation, autofill and password saving are off. The webview's devtools and context menu are on in development builds only; on macOS the devtools are Safari's Web Inspector, from Safari's Develop menu.
- Documents close when their window closes and when the app quits.
- On Windows the webview's storage lives in the app's data directory, under `webview`. On macOS it is WebKit's own store for the app.

## Platforms

| Platform | `<iframe>`                                                                                         |
| -------- | -------------------------------------------------------------------------------------------------- |
| Windows  | WebView2, when the WebView2 runtime is installed. It ships with Windows 11 and current Windows 10. |
| macOS    | WKWebView, part of macOS.                                                                          |
| Linux    | An empty box that fires `error`.                                                                   |

`skFeatures.iframe` is `false` wherever there is no webview: on Linux, on Windows without the WebView2 runtime, and in a host built without the `webview` Cargo feature. Without the feature the element also prints a warning naming it; see [Features and size](/embedding/features/).

### macOS (since 0.5)

The document runs in a different engine on each system, so test a page from the web on both. Where the two webviews differ:

- **Cookies.** The document's top-level page is Skathi's, so a page from the web is a third party in it. WebKit blocks third-party cookies: a page that keeps its sign-in in cookies has to ask for them with `document.requestStorageAccess()`.
- **Full screen.** `requestFullscreen()` inside the document is refused on macOS, `allowfullscreen` or not.
- **Keys.** Alt combinations stay with the app on Windows; on macOS, Command shortcuts the document leaves unused reach the app.
