## Upgrading

### Text with no `line-height` is `normal`

A document's text now starts at CSS's initial `line-height: normal`. Before, text whose line height no rule declared got 1.618 of its font size, so every line was about 0.4 em taller than in a browser. Interfaces that never declare `line-height` (most of those written for the web) now come out at the browsers' heights: buttons, menu rows and labels lose the extra room.

To keep the old look, declare it once:

```css
html {
  line-height: 1.618;
}
```

### `normal` follows the font

`line-height: normal` is no longer a fixed 1.2 of the font size. It comes from the first available font of the element's `font-family`: its ascent, descent and line gap, rounded as Chromium rounds them, so Segoe UI at 16px is 21px tall and Arial 18px, as in Chromium. It inherits as the keyword, and each element resolves it for its own font and size. A line whose glyphs fall back to another font, such as Chinese text in a Latin font, does not yet grow to that font's height.

### White space at the edges of a flex item

A space at the start or end of a flex or grid item's text is removed, as in the browsers. A label written on its own line after an icon (`<svg/>\n  Open a link\n`) no longer makes the button a space wider. The same holds for the text of a `display: block` or `inline-block` element and of an absolutely positioned one; text inside an inline `<span>` beside other text keeps its spaces.

## Text

### Glyph positions by size

On Windows and Linux a glyph is placed in steps that depend on its size: quarters of a pixel below 12px, thirds up to 16px, halves from 17px and whole pixels from 34px (in device pixels), instead of quarters at every size. Small text keeps its spacing, large text stops caching four rasterizations of every glyph, and the glyph atlas holds 7 to 23% fewer tiles depending on the display scale. macOS follows its own version of the table, below.

### Scaled text settles

Text under a `transform` that scales it used to be drawn from glyphs rasterized at the untransformed size and resampled, so `scale(1.14)` came out soft. Now, once a transform has stopped changing for 200 ms, the text under it is rasterized again at the size it is shown at, and matches text laid out at that size. That holds inside a cached subtree and in a scrolling list too. A transform that keeps changing, such as a running animation, stays resampled rather than rasterizing its glyphs every frame, and nothing keeps running once the text has settled.

### `font-smoothing`

The new inherited `font-smoothing` property picks grayscale or subpixel text: `auto` (the platform's rule, as before), `antialiased` (always grayscale) or `subpixel-antialiased`. The prefixed `-webkit-font-smoothing` is read as the same property, and `sk check` suggests the unprefixed spelling. Set the app's default on the root:

```css
html {
  font-smoothing: antialiased;
}
```

A Skathi window has a Mica backdrop by default, and Windows draws ClearType only over an opaque one, so under `auto` the text in a default window is grayscale even when ClearType is on in the system. `subpixel-antialiased` draws ClearType in such a window anyway. It is right only where the text sits on opaque content, such as a panel with a solid background; over a see-through part of the window the colour fringes of the glyph edges stay visible. On macOS text is always grayscale, and `antialiased` turns off the thickening described below.

### `font-dilation`

Windows gives light text on a dark ground less weight than dark text on a light one, so a dark interface reads thinner than its light twin. `font-dilation: luminance`, a Skathi property that inherits, gives text more weight the lighter it is, as macOS does: light text at 14px gains 6 to 15% ink, dark text is unchanged. It works with grayscale and ClearType text and costs no glyph cache space. On macOS, where CoreGraphics already does this, it changes nothing.

### Text on macOS as native apps draw it

Text on macOS was darkened twice: CoreGraphics thickens each glyph by an amount its colour selects, and Skathi's Metal renderer then applied the gamma and contrast correction that DirectWrite text gets on Windows. Coverage is now blended as it is, the way macOS composites a label, and the thickening is chosen from the colour's linear luminance, as CoreGraphics chooses it, so light grey, green and red text get the weight they get in a native app (red used to get black's). Glyphs are placed in the steps macOS uses for their size (thirds of a pixel at 13px on a 1x display, halves at 13px on a Retina display, whole pixels from 17px on Retina) and rounded down as macOS rounds them, and small text keeps the system's vertical hinting. `font-weight: 500` on the system font selects its Medium design, which it drew as Regular before, and large text no longer loses a column of pixels at a glyph's edge. Against CoreText drawing the same line in the same colour, every pixel of the composited text now matches, at 13 and 24px, on 1x and Retina displays, for black, white, greys and saturated colours. Monochrome SVG icons are blended the same way.

`font-smoothing: antialiased` now does on macOS what it does in Safari: it turns the thickening off, so text is thinner, light text on a dark ground most of all. Tailwind's `antialiased` class sets it, so an app that uses that class draws thinner text on macOS than before, as the same page does in Safari.

### `will-change: transform` moves text as a layer

Text under a moving `translate()` is placed on whole pixels in every frame, so it steps by a pixel against the borders and lines of its box. Inside an element with `will-change: transform` the text now moves with the box instead, and once the box has been still for 200 ms it is drawn sharp where it stopped.

### `line-metrics` and `line-leading`

Two new inherited Skathi properties build a line the way macOS builds a label's. `line-metrics: snapped` rounds the font's ascent and descent to whole pixels, leaves out the line gap and rounds the descent up where rounding would cut into a descender, so the baseline falls on a whole pixel and `line-height: normal` is that box. `line-leading: above` puts all the leading above the font's box instead of half above and half below. Together they reproduce where AppKit and SwiftUI put a label: 13px text is 16px tall with its baseline at 13, and a 24px button that centres it puts the baseline at 17.

```css
html {
  line-metrics: snapped;
  line-leading: above;
}
```

The rules are the same on every platform, and the defaults, `auto` and `split`, are CSS's. They apply to layout, painting, selection and the caret, `vertical-align`, `text-box-trim`, baseline alignment, text fields and `<sk-editor>`; in a line that mixes sizes, each run's box comes from its own font, and the line reaches as far above and below the baseline as its runs do.

## Fixes

- A `transform-origin` from a class now applies to a `transform` set in a `style` attribute or by `@keyframes`; before, it was replaced by the default `50% 50%`. A rule that sets only `transform-origin` no longer cancels a `transform` from an earlier rule.

- Windows: while a window is moved with `appWindow.startDragging()`, the page keeps running (timers, `requestAnimationFrame`, animations, video, `<sk-surface>`) instead of freezing until the button is released. The move starts after the `mousedown` handler returns, and only while the left button is still held. ([#110](https://github.com/argon-chat/skathi/issues/110))
