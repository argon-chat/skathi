## Upgrading

### Text with no `line-height` is `normal`

A document's text now starts at CSS's initial `line-height: normal`. Before, text whose line height no rule declared got 1.618 of its font size, so every line was about 0.4 em taller than in a browser. Interfaces that never declare `line-height` (most of those written for the web) now come out at the browsers' heights: buttons, menu rows and labels lose the extra room.

To keep the old look, declare it once:

```css
html {
  line-height: 1.618;
}
```

### `normal` follows the font

`line-height: normal` is no longer a fixed 1.2 of the font size. It comes from the first available font of the element's `font-family`: its ascent, descent and line gap, rounded as Chromium rounds them, so Segoe UI at 16px is 21px tall and Arial 18px, as in Chromium. It inherits as the keyword, and each element resolves it for its own font and size. A line whose glyphs come from another font, such as Chinese text in a Latin font, grows where that font's box is taller, below.

### White space at the edges of a flex item

A space at the start or end of a flex or grid item's text is removed, as in the browsers. A label written on its own line after an icon (`<svg/>\n  Open a link\n`) no longer makes the button a space wider. The same holds for the text of a `display: block` or `inline-block` element and of an absolutely positioned one; text inside an inline `<span>` beside other text keeps its spaces.

### Text on Windows and Linux is drawn as on a Mac

The new `"textRendering"` setting in sk.config.json picks the rasterizer, and its default on Windows and Linux is `"skathi-mode"`, below, which is experimental. Text there is grayscale and a little heavier than before, light text on a dark ground most of all. To keep DirectWrite with ClearType, as 0.8 drew it:

```json
{
  "textRendering": "optimized"
}
```

`SK_TEXT_RENDERING=optimized` in the environment does the same without a rebuild.

## Text

### Skathi mode (experimental)

Skathi now has its own glyph rasterizer, and on Windows and Linux it draws every glyph the way macOS does. It reads the font's outlines without hinting, thickens them by an amount the text colour's luminance selects (sideways by the amount, upwards by twice it, the baseline kept, in five steps as CoreGraphics takes them), puts the x-height and cap height of small text on whole pixels as macOS's vertical hinting does, and blends the coverage linearly, with no gamma or contrast correction. It is `"skathi-mode"`, the default on Windows and Linux; `"optimized"` keeps the platform's rasterizer (DirectWrite with ClearType, swash), and on macOS both draw with CoreText. The [text rendering guide](/guides/text-rendering/#two-rendering-modes) says when to pick which. The mode is experimental in this release: it is the default so that it is tried on real apps and displays, its output may still change, and `"optimized"` is the stable choice.

Measured on Windows against CoreText rendering the same text (Manrope 400 and 600; 11, 13, 16 and 24px; 1x and 2x; black, white, grey and coloured text; 48 cases), glyph masks differ by 0.25 to 1.1 levels in 255 on average per case; DirectWrite's differ by 33 to 36. Ink stays within 0.1% of CoreText's. Against 0.8 on Windows, light text on a dark ground has 10 to 22% more ink. On Linux the same rasterizer reads the outlines through swash and produces the same masks, byte for byte, as on Windows.

In this mode `font-smoothing: subpixel-antialiased` is ignored, `font-dilation` changes nothing, and `font-smoothing: antialiased` turns the thickening off, as in Safari. Emoji are drawn as before. Each colour step needs its own glyph in the atlas, so text in several colours takes more atlas tiles than in `"optimized"` mode, and a glyph takes up to 4.6 times as long to rasterize the first time it is drawn (2 to 5 µs).

### Glyph positions by size

On Windows and Linux a glyph is placed in steps that depend on its size: quarters of a pixel below 12px, thirds up to 16px, halves from 17px and whole pixels from 34px (in device pixels), instead of quarters at every size. Small text keeps its spacing, large text stops caching four rasterizations of every glyph, and the glyph atlas holds 7 to 23% fewer tiles depending on the display scale. macOS follows its own version of the table, below.

### Scaled text settles

Text under a `transform` that scales it used to be drawn from glyphs rasterized at the untransformed size and resampled, so `scale(1.14)` came out soft. Now, once a transform has stopped changing for 200 ms, the text under it is rasterized again at the size it is shown at, and matches text laid out at that size. That holds inside a cached subtree and in a scrolling list too. A transform that keeps changing, such as a running animation, stays resampled rather than rasterizing its glyphs every frame, and nothing keeps running once the text has settled.

### `font-smoothing`

The new inherited `font-smoothing` property picks grayscale or subpixel text: `auto` (the platform's rule, as before), `antialiased` (always grayscale) or `subpixel-antialiased`. The prefixed `-webkit-font-smoothing` is read as the same property, and `sk check` suggests the unprefixed spelling. Set the app's default on the root:

```css
html {
  font-smoothing: antialiased;
}
```

A Skathi window has a Mica backdrop by default, and Windows draws ClearType only over an opaque one, so under `auto` the text in a default window is grayscale even when ClearType is on in the system. `subpixel-antialiased` draws ClearType in such a window anyway. It is right only where the text sits on opaque content, such as a panel with a solid background; over a see-through part of the window the colour fringes of the glyph edges stay visible. On macOS text is always grayscale, and `antialiased` turns off the thickening described below.

### `font-dilation`

DirectWrite gives light text on a dark ground less weight than dark text on a light one, so a dark interface reads thinner than its light twin. In `"optimized"` mode `font-dilation: luminance`, a Skathi property that inherits, gives text more weight the lighter it is, as macOS does: light text at 14px gains 6 to 15% ink, dark text is unchanged. It works with grayscale and ClearType text and costs no glyph cache space. On macOS, where CoreGraphics already does this, it changes nothing.

### Text on macOS as native apps draw it

Text on macOS was darkened twice: CoreGraphics thickens each glyph by an amount its colour selects, and Skathi's Metal renderer then applied the gamma and contrast correction that DirectWrite text gets on Windows. Coverage is now blended as it is, the way macOS composites a label, and the thickening is chosen from the colour's linear luminance, as CoreGraphics chooses it, so light grey, green and red text get the weight they get in a native app (red used to get black's). Glyphs are placed in the steps macOS uses for their size (thirds of a pixel at 13px on a 1x display, halves at 13px on a Retina display, whole pixels from 17px on Retina) and rounded down as macOS rounds them, and small text keeps the system's vertical hinting. `font-weight: 500` on the system font selects its Medium design, which it drew as Regular before, and large text no longer loses a column of pixels at a glyph's edge. Against CoreText drawing the same line in the same colour, every pixel of the composited text now matches, at 13 and 24px, on 1x and Retina displays, for black, white, greys and saturated colours. Monochrome SVG icons are blended the same way.

`font-smoothing: antialiased` now does on macOS what it does in Safari: it turns the thickening off, so text is thinner, light text on a dark ground most of all. Tailwind's `antialiased` class sets it, so an app that uses that class draws thinner text on macOS than before, as the same page does in Safari.

### `will-change: transform` moves text as a layer

Text under a moving `translate()` is placed on whole pixels in every frame, so it steps by a pixel against the borders and lines of its box. Inside an element with `will-change: transform` the text now moves with the box instead, and once the box has been still for 200 ms it is drawn sharp where it stopped.

### Text keeps its shape while it moves

Under a moving `translate()` each glyph used to be placed on its own, so the gaps between letters changed by up to half a pixel from frame to frame and words seemed to shimmer. The translation is now rounded once for the whole text, and letters and lines keep their distances while it moves. Text that is scaled, rotated or moved as a layer is resampled with its edges intact: a glyph's outermost pixels fade out past its box as they should, instead of being cut off where its box ends, which made letters wobble against each other by up to 0.9 px under a running `scale()`. It now stays under 0.2 px. A plain rectangle, a background or a rule with no border or rounded corner, now has antialiased edges under a fractional translation, a scale or a rotation, where it used to step by whole pixels, so inside a `will-change: transform` box the text and the box's lines move together. ([#108](https://github.com/argon-chat/skathi/issues/108))

### `line-metrics` and `line-leading`

Two new inherited Skathi properties build a line the way macOS builds a label's. `line-metrics: snapped` rounds the font's ascent and descent to whole pixels, leaves out the line gap and rounds the descent up where rounding would cut into a descender, so the baseline falls on a whole pixel and `line-height: normal` is that box. `line-leading: above` puts all the leading above the font's box instead of half above and half below. Together they reproduce where AppKit and SwiftUI put a label: 13px text is 16px tall with its baseline at 13, and a 24px button that centres it puts the baseline at 17.

```css
html {
  line-metrics: snapped;
  line-leading: above;
}
```

The rules are the same on every platform, and the defaults, `auto` and `split`, are CSS's. They apply to layout, painting, selection and the caret, `vertical-align`, `text-box-trim`, baseline alignment, text fields and `<sk-editor>`; in a line that mixes sizes, each run's box comes from its own font, and the line reaches as far above and below the baseline as its runs do.

### Fallback fonts grow the line

Under `line-height: normal` a line with glyphs from a font other than the first one, a later family of `font-family` or the system's fallback, is as tall as that font's box needs: its rounded ascent and descent with half its line gap above and half below, on the shared baseline, as Chromium builds it. Manrope at 16px is 22px tall; with a Private Use Area glyph from Alcarin Tengwar, whose line gap reaches further below, the line is 23px, as in Chromium. Under `line-metrics: snapped` the other font's snapped box counts. A line without such glyphs keeps the first font's height, and a declared `line-height` never grows. ([#106](https://github.com/argon-chat/skathi/issues/106))

### `font-size-adjust`

`font-size-adjust` draws the fonts of a text at the size that matches their x-height: `from-font` sizes every fallback font to the first font's, and a number sizes the first font too, so that its x-height is that fraction of the font size. `cap-height`, `ch-width` and `ic-width` match by another metric. The computed `font-size` and `em` stay as declared. ([#106](https://github.com/argon-chat/skathi/issues/106))

### `font-family` lists

Each character is now drawn with the first family of the `font-family` list that has a glyph for it, as in browsers, on Windows, macOS and Linux alike. An `@font-face` family after an installed one is reached, a face is used only for the characters its `unicode-range` covers, and one whose range covers a character it has no glyph for passes it to the next family instead of to the system's fallback. On macOS and Linux only the first family was used before, and `unicode-range` subsets of one family were not told apart. A character no font has is the first family's missing glyph on every platform; macOS drew Core Text's LastResort symbol for it. The [text rendering guide](/guides/text-rendering/#characters-the-font-lacks) has the order. ([#106](https://github.com/argon-chat/skathi/issues/106))

## Packaging

`sk package` turns a release build into what people install. It runs `sk publish`, then writes the formats the new `"package"` section of sk.config.json lists for the system it runs on into `dist/package`: who publishes the app, its reverse-DNS id, the icon every format scales its images from, the file types it opens and the URL schemes it handles. Most of it defaults from the keys the app already has. `--from <dir>` packages a folder built another way, such as the output of a Rust program that embeds Skathi, and `sk check` reports a mistake in the section as SK8001 or SK8002 before anything is built. The [packaging guide](/guides/packaging/) walks through it.

On Windows it writes an MSIX, without the Windows SDK: the program and its files, a manifest that declares the app as a full-trust desktop app with its file types and URL schemes, tile and taskbar images from the icon at every scale and target size with their unplated variants, the `resources.pri` index Windows chooses among them with (the same bytes `makepri` writes), and the block map Windows verifies the package against. Inside a package, `appPermissions` and `navigator.permissions` read the app's own switch in Windows' privacy settings, where a packaged app is listed by name, instead of the switch for all desktop apps. With `"appInstaller"` it also writes an `.appinstaller` file, through which installed copies update from a URL. The package's publisher must be the signing certificate's subject, character for character, and `sk package` prints the one it wrote; signing is still a `signtool` step of your own.

On macOS it writes a disk image: the signed app, a link to Applications, and the Finder window they open in, with its size, icon positions and background from `"dmg"` in the config. The layout is written as Finder's own `.DS_Store` rather than by scripting Finder, so it builds headless on a CI runner. With `"notarize"`, the app and then the image go to Apple's notary service and get their tickets stapled; the credentials are a keychain profile or an App Store Connect API key read from environment variables, and a key written into sk.config.json is refused. Extra entitlements for the signed app go in the new `macos.entitlements`.

For Linux it writes an AppImage, on any system, Windows and macOS included: `sk package` builds the squashfs itself and puts the pinned AppImage type-2 runtime in front of it, so neither `mksquashfs` nor `appimagetool` is needed. The image holds the program and its files, a desktop entry with the app's categories, file types and URL schemes (a link reaches `appLaunch.url` also in an app that opens files, where the entry passes it as a plain argument), the icon at the hicolor sizes and AppStream metainfo. `"updateInformation"` is embedded for AppImageUpdate, with a `.zsync` beside the image when `zsyncmake` is installed, and `"signKey"` embeds a GnuPG signature as appimagetool does. Skathi's Linux hosts are built on Ubuntu 22.04, so an image needs glibc 2.35 or newer (Ubuntu 22.04, Debian 12, Fedora 36, RHEL 10 or later), and `sk package` prints the floor of the host it packages.

## Fixes

- `text-box-trim` trimmed the font's descent too much from the top of a line, and with a `text` or `cap` bottom edge from the bottom too, so a trimmed box was shorter than its glyphs. It now leaves exactly the edges `text-box-edge` names.
- A `transform-origin` from a class now applies to a `transform` set in a `style` attribute or by `@keyframes`; before, it was replaced by the default `50% 50%`. A rule that sets only `transform-origin` no longer cancels a `transform` from an earlier rule.

- Windows: while a window is moved with `appWindow.startDragging()`, the page keeps running (timers, `requestAnimationFrame`, animations, video, `<sk-surface>`) instead of freezing until the button is released. The move starts after the `mousedown` handler returns, and only while the left button is still held. ([#110](https://github.com/argon-chat/skathi/issues/110))
